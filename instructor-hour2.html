Understand it · 1 minute

The hour in one breath

  1. The request: "Italy's sell-through number looks low. The pipeline has been green for weeks and no alert fired. Can you confirm it is fine?"
  2. The catch: two nightly pipelines each carry one reasonable-looking channel filter. Italy silently drops one distributor (210 rows); Japan silently drops another (105 rows). Nothing errors, so nobody noticed Japan at all.
  3. What students do: the loop Detect → Diagnose → Correct → Prevent. Count raw rows against pipeline rows per distributor (starting from the list of distributors that should exist), read the model and have Claude explain it, prove the cause with a count of exactly 105, delete one line, then have Claude write a dbt test and break the pipeline on purpose to watch it fail.
  4. What they leave with: a fixed analytics.japan_sell_through (1,050 rows, was 945) and a guard, tests/assert_japan_no_dropped_distributors.sql, that they have seen go red once.

The line to repeat all hour: automation does the work, you own the outcome.

Understand it · the three things that must land

What to emphasize

If the room forgets everything else, these three survive.

#Must landWhy it matters
1A green run is not a right number. Job status tells you the SQL executed; only a reconciliation against the source tells you the number is right.Every silent failure this hour (the NULL opener, both channel filters, the uncalibrated threshold) ran green. If they leave thinking "monitor the job", the hour failed.
2Reconcile per key, starting from what should exist. Start from the list of distributors, then count each one's rows in the source and in the pipeline, so a distributor with nothing in the pipeline shows up as a 0.A check that starts from the pipeline's own rows never sees the missing distributor: it inherits the pipeline's blind spot. The guide's "Why start from the list matters" box says this in plain words; read it aloud.
3A guard you have never seen fail is a guard you trust on faith. Put the bad line back, watch the test go red, take it out again.This is the beat people remember and the one you never cut. It turns "we added a test" into "we know the test works".
And the stance to model, not just say

Claude is an investigative companion, not an oracle. Run every query it writes against the warehouse before you believe it, out loud, every time.

Understand it · 3 minutes

The tables, simply

One raw feed, one lookup, two pipelines built from them, and one table borrowed from Hour 1 for the opener.

rst.sell_through 2,730 rows · the source

What it is: weekly retail sales. One row = one distributor, one product, one week. Every sale_date is a Monday: 105 Mondays, 2024-01-01 to 2025-12-29.

By market: Japan 1,050 rows · Italy 945 · Indonesia 735. This is the truth the pipelines should copy.

Like the till receipts: what actually got sold, before anyone filtered anything.

rst.distributors 12 distributors

What it is: who sells the product. One row per distributor, with a channel_type: branded_retail (PMI's own stores), partner_retail (third-party shops) or ecommerce.

Japan has 5: Branded 1, Partner 2, Ecommerce 3 (id 3), Branded 4, Partner 5. Italy has 4, including Partner 2 (id 7).

Like the supplier list: one row per partner, safe to join, and where the channel lives.

analytics.japan_sell_through · analytics.italy_sell_through 945 Japan rows (should be 1,050)

What they are: the two nightly pipelines (dbt views): sell-through for one market, with the distributor's name and channel attached. Same grain as the source.

Today: Japan stages 945 of 1,050; Italy stages 735 of 945. Both have been "green" all along.

Like the weekly report someone builds from the receipts: it looks complete, and nobody checks it against the till.

clr.lifecycle_events 15,597 rows · opener only

What it is: the consumer journey table from Hour 1. Used only for the three-minute NULL opener.

The fact: only 74 rows have a campaign_id (all campaign 1); the other 15,523 are NULL.

Like a form where most people left "campaign" blank: blank is not "not campaign 1", it is "unknown".

945 shows up twice: don't let it confuse you

Italy's source has 945 rows, and Japan's planted pipeline also has 945 rows. They are unrelated. When a student says "945", ask "Japan staged, or Italy source?"

Understand it · 3 minutes

The problem, in plain words

Two pipelines, two one-line rules, two whole distributors gone.

Japan (the lab): a rule hidden in the join

join {{ source('rst', 'distributors') }} d
    on d.distributor_id = s.distributor_id
   and d.channel_type <> 'ecommerce'   -- exclude non-store channels
where s.market_code = 'JP'

The join matches a sale to its distributor and requires the distributor not to be ecommerce. Japan has exactly one ecommerce distributor, JP Ecommerce Distributor 3, so every one of its 105 weekly rows fails the join and never enters the pipeline. That is 17,721 units and about €88,700 of sales, 6.9% of Japan's units, missing from every dashboard. No error: a join that matches nothing is perfectly legal SQL.

StageRowsIn plain words
source, Japan1,050every weekly sale that happened
the join's channel rule−105JP Ecommerce Distributor 3, all of it, on the floor
pipeline, Japan945what the dashboard shows. Job status: green

Italy (the story Marketing noticed): a rule in the WHERE

and d.channel_type in ('branded_retail', 'ecommerce') -- limit to reportable retail channels keeps two of three channels, so Italy's one partner_retail distributor, IT Partner Distributor 2, loses all 210 rows (25,461 units). Marketing noticed because the number looked low. Students only detect Italy in the main lab; they fix Japan. Fixing Italy is Challenge 1, and it comes with a sign-off question.

Why this is the same bug as the opener

A plausible-looking condition quietly removes legitimate rows. In the opener it was campaign_id <> 1 against NULLs; here it is a channel rule in a join. Different column, same class of failure: a filter nobody questioned, and no error to tell you.

The fix is to delete the line, not move it

Moving and d.channel_type <> 'ecommerce' from the join into the where drops the same 105 rows from a different place. The rule is wrong, not misplaced. Whether ecommerce should count is a business decision nobody was asked about, which is the bridge to Hour 3.

Understand it · gotchas

What you need to know

  • One folder for Hours 1 and 2. On the VM it is C:\Users\labadmin\Downloads\setup\horizon_dbt. The profiles.yml, sources file and schema macro from the pre-flight all carry over; there is nothing new to configure.
  • The two pipelines may not exist on the VM. Students check for models\japan_sell_through.sql and models\italy_sell_through.sql and paste them from the guide if missing. Tell them to paste without reading for the bug: finding it from the data is the lab.
  • Always --select. dbt run --select italy_sell_through japan_sell_through (setup) and dbt run --select japan_sell_through (afterwards). A bare dbt run also rebuilds the Hour 1 model and any half-finished challenge model, which is noise at best and an error at worst.
  • The whole hour stays on Sonnet. The fix is one line and the tests come from a precise list: typing, not judgment. Say it once so nobody hunts for Opus.
  • Students fix the model by hand. No prompt for the fix: they delete one line themselves. Claude does two jobs this hour: explain the planted model in plain English (Step 2b) and write the test from a precise description (Step 4a). The reconciliation query is given in the guide, explained line by line.
  • The guard must fail before it is trusted. The "prove the guard bites" beat is non-negotiable. Students who skip it have a test they have never seen work.
  • Challenge 3 numbers assume the fixed model. On the planted 945-row model the spread query returns 9 series instead of 10, and 0.5×/2× flags 5 weeks, not 6. If a student reports 9 or 5, their Japan model still has the bad line in.
  • Trailing semicolons break dbt tests. dbt wraps the test in its own query. Almost every "test errored" is a pasted ;.
  • Reset between classes. Once a student has fixed Japan, their view reads 1,050. On your Mac, make plant puts both defects back and removes lab artefacts.

The hour's queries, as one SQLTools file

Paste the whole block into one SQLTools file before class; select one query at a time and press Ctrl+E Ctrl+E.

-- Opener                                                    expect 74 / 0 / 15,523
select count(*) from clr.lifecycle_events where campaign_id = 1;
select count(*) from clr.lifecycle_events where campaign_id <> 1;
select count(*) from clr.lifecycle_events where campaign_id is distinct from 1;

-- Pre-flight                                                expect 945 planted, 1,050 fixed
select count(*) from analytics.japan_sell_through;

-- Step 1 · query 1: totals                                   expect 1,050 / 945 planted (1,050 fixed)
select
  (select count(*) from rst.sell_through
    where market_code = 'JP')                       as in_source,
  (select count(*) from analytics.japan_sell_through) as in_pipeline;

-- Step 1 · query 2: the reconciliation                        expect 9 rows; 210 (IT) and 105 (JP) missing
select market_code, distributor_name, in_source, in_pipeline,
       in_source - in_pipeline as missing
from (
  select d.market_code, d.distributor_name,
         (select count(*) from rst.sell_through s
           where s.distributor_id = d.distributor_id)         as in_source,
         (select count(*) from analytics.japan_sell_through j
           where j.distributor_id = d.distributor_id)
       + (select count(*) from analytics.italy_sell_through i
           where i.distributor_id = d.distributor_id)         as in_pipeline
  from rst.distributors d
  where d.market_code in ('JP', 'IT')
) counts
order by missing desc;

-- Step 2 · the proof                                          expect 105
select count(*) as rows_the_rule_removes
from rst.sell_through s
join rst.distributors d on d.distributor_id = s.distributor_id
where s.market_code = 'JP'
  and d.channel_type = 'ecommerce';

-- Challenge 3 · the real spread (on the FIXED model)          expect 10 rows, 0.41x to 1.57x
select distributor_id, product_code, min(units_sold), round(avg(units_sold)) as avg_units, max(units_sold),
       round(max(units_sold)::numeric / avg(units_sold), 2) as max_over_avg,
       round(min(units_sold)::numeric / avg(units_sold), 2) as min_over_avg
from analytics.japan_sell_through group by 1, 2 order by 1, 2;

The Step 4 test

dbt test --select japan_sell_through → PASS=1 on the fixed model; FAIL 1 with the line back in.

-- Guard: fails (returns a row) for every Japan distributor whose rows did not all reach the pipeline.
select distributor_name, in_source, in_pipeline
from (
    select d.distributor_name,
           (select count(*) from {{ source('rst', 'sell_through') }} s
             where s.distributor_id = d.distributor_id) as in_source,
           (select count(*) from {{ ref('japan_sell_through') }} j
             where j.distributor_id = d.distributor_id) as in_pipeline
    from {{ source('rst', 'distributors') }} d
    where d.market_code = 'JP'
) counts
where in_pipeline < in_source

★★ 3 · Calibrate the alarm (automation bias)

Spread on the fixed model: 10 series, normal weeks from 0.41× to 1.57× of their own average. Claude's usual 0.5× / 2× → FAIL 6 (all six are low weeks between 0.41× and 0.5×). 0.35× / 1.75× → PASS. With the Step 4 test also present, dbt test --select japan_sell_through → PASS=2 (PASS=3 if Challenge 2's test is there too).

-- Flags any week above 1.75x (or below 0.35x) of that distributor/product's own average.
-- Observed Japan range is 0.41x to 1.57x, so these limits sit just outside normal.
with hist as (
    select distributor_id, product_code, avg(units_sold) as avg_units
    from {{ ref('japan_sell_through') }}
    group by 1, 2
)
select s.distributor_id, s.product_code, s.sale_date, s.units_sold, round(h.avg_units) as avg_units
from {{ ref('japan_sell_through') }} s
join hist h using (distributor_id, product_code)
where s.units_sold > 1.75 * h.avg_units     -- limits: upper 1.75, lower 0.35
   or s.units_sold < 0.35 * h.avg_units
Say

"A threshold copied from the assistant without this check is calibrated by luck. Automation bias: a confident number from a tool gets checked less than the same number from a colleague. The fix is boring: look at the real spread first."
