Hour 3 · WA3908 · Unpack → Clarify → Prove → Specify

Theme: shift left

Both bugs from Hours 1 and 2 were "reasonable scoping rules" that someone added without asking anyone. The cheapest place to catch a wrong assumption is before the code exists.

A request is intent, not a specification. Align first, build once.

Follow along. You will not build anything this hour. You will bring engineering reality to a request before a line of code is written, and prove two things against the warehouse. Four steps: Unpack → Clarify → Prove → Specify.

Shift left means moving the checking to the left of the project timeline (Request, Design) instead of the right (Test, Operate). In Hour 1 the consent-ledger bug was caught in review, 25 minutes after the draft. In Hour 2 the ecommerce filter was caught in Operate, months later, 105 rows short. This hour the same class of mistake gets caught before anyone opens an editor. A wrong assumption fixed at Request costs 1x; after delivery it can cost up to 100x. What moves left is not the test suite. It is the questions.

What you leave with

Five clarifying questions, a four-line feasibility gate, and the requirements Marketing never said.

Words you will hear

Every term this hour uses, in plain English. Each one links to the full glossary.

Words you will hear Full glossary →
TermPlain English
Request vs specificationA request says what someone wants, in their words ("real-time"). A specification says exactly what will be built, in terms you can test ("refreshed by 07:00 each morning, as-of date shown on every number").
Shift leftDo the checking at Request and Design, before any code exists, instead of at Test and Operate. The thing that moves left is the questions.
Feasibility verdictThe only three answers you give on a requirement: buildable as asked · buildable with a change · not as asked. Each one comes with a number from the warehouse.
Functional requirementWhat the thing must do: "show the weekly conversion count per market".
NFR (non-functional requirement)How the thing must behave: refresh cadence, cost, reliability, who may see it, where the data lives, which regulation applies. Nobody states these. Everybody assumes them.
Conversion · lifecycle stageIn PMI usage, an adult smoker switching to a smoke-free product. In HORIZON a consumer's journey is recorded as lifecycle stages, registration → trial → conversion → retention → churn, in clr.lifecycle_events.lifecycle_stage. The word "conversion" in a request does not say which stage, or how to count it.
Consent · marketing permissionmpl.consent_records: whether a consumer allowed marketing (marketing_allowed) and from when (consent_date). It is a ledger, a table that keeps history, about 2.5 rows per consumer, so a join to it multiplies rows (Hour 1).
Age band · the under-25 ruleclr.consumers.age_band; '18-24' is the under-25 band. In HORIZON, marketing to under-25s is forbidden in Italy and Indonesia (0% marketing-allowed, by design) and allowed in Japan.
Sell-throughRetail sales from the distributor or retailer to the end consumer (as opposed to sell-in: PMI's shipments to the distributor). rst.sell_through holds one row per distributor, product and week; every sale_date is a Monday.
GrainWhat one row represents. Sell-through's grain is one distributor, one product, one week.
Batch-fed vs real-timeBatch: data arrives in scheduled loads (nightly, weekly). Real-time: each event arrives within seconds through a stream. HORIZON is batch-fed.
Power BI Desktop vs ServiceDesktop is the free authoring app on a Windows PC: you open a .pbix file and refresh it yourself. Service is Microsoft's cloud workspace with scheduled refresh, sharing and access control. In the HORIZON scenario Marketing has Desktop on their PCs and there is no shared Service workspace, so "a dashboard" today means a file someone refreshes and emails. You will not open Power BI this hour.
Data residencyThe rule that data about a market's consumers stays in an approved jurisdiction. A dashboard that joins three markets is a residency decision, not just a join.
RegulatorsMHLW (Japan's Ministry of Health, Labour and Welfare), AAMS/EU (Italy's tobacco monopolies authority, plus EU-level rules), BPOM (Indonesia's drug and food control agency). Three regulators, two regions (APAC, EU).
As-of dateThe date the source data was last loaded, printed on every number. "Refreshed each morning" describes the report. The as-of date describes the data.

Running a query in SQLTools

In the VS Code sidebar open SQLTools (the database icon); if HORIZON shows as disconnected, right-click it → Connect; then right-click HORIZON → New SQL File, paste the query, then click Run on active connection just above it (or select the text and press Ctrl+E twice). (a) Is "real-time" possible? Sell-through is weekly.

What this checks How often sell-through data arrives: how many rows, how many distinct weeks, and whether any date is not a Monday.

select count(*) as rows, count(distinct sale_date) as distinct_weeks,
       count(*) filter (where extract(isodow from sale_date) <> 1) as non_monday_rows,
       min(sale_date), max(sale_date)
from rst.sell_through;
-- 2,730 rows · 105 distinct weeks · 0 non-Mondays · 2024-01-01 → 2025-12-29

Expected result 2,730 rows 105 distinct weeks 0 non-Mondays 2024-01-01 → 2025-12-29

Reading the query: extract(isodow from sale_date) is the ISO day of the week, Monday = 1 through Sunday = 7, so non_monday_rows counts rows whose date is not a Monday. count(*) filter (where ...) counts only the rows that match the condition. 0 non-Mondays and 105 distinct dates across two years means the feed is one row per distributor, product and week. There is no event stream to be real-time about.

Verdict on "real-time": buildable with a change Nothing arrives faster than weekly, so the honest offer is a refresh each morning (or weekly), with the as-of date on every number.

(b) Is a uniform cross-market view legal? Under-25 marketing is forbidden in Italy and Indonesia.

What this checks Per market, what share of under-25 consent rows allow marketing.

select c.market_code,
       count(*) filter (where c.age_band = '18-24') as under25_rows,
       count(*) filter (where c.age_band = '18-24' and m.marketing_allowed) as under25_mktg_ok,
       round(100.0 * count(*) filter (where c.age_band = '18-24' and m.marketing_allowed)
             / nullif(count(*) filter (where c.age_band = '18-24'), 0), 0) as pct
from clr.consumers c left join mpl.consent_records m using (consumer_id)
group by 1 order by 1;
-- ID 0% · IT 0% · JP 73%

Expected result ID 0% IT 0% JP 73% JP: 675 of 924 under-25 consent rows

Reading the query: clr.consumers is LEFT JOINed to the consent ledger on consumer_id, so each consumer appears once per consent row (about 2.5 times) and the counts are consent rows, not people (Japan: 675 of 924 under-25 consent rows allow marketing; counted as people, 319 of 359 under-25 consumers). A LEFT JOIN keeps every consumer even if no consent row matches (an INNER JOIN would drop those consumers). In HORIZON every consumer has at least one consent row, so the choice does not change these counts; it is there so a consumer with no consent would still appear, with marketing_allowed blank. For a legality check the rows-versus-people difference does not matter: the number that matters is zero or not zero. nullif(..., 0) stops a division by zero in a market with no under-25 rows.

Verdict on an under-25 cross-market segment: not as asked Non-compliant in IT and ID. Scope to Japan or drop the segment.

The AI connection

Marketing's ambiguous request and a vague prompt fail the same way. "Build me a dashboard" gets you a plausible wrong build; "draft me a model" gets you plausible wrong SQL. In both cases the gap is filled with the most likely guess, silently; this morning the guess was "latest consent". A model only knows what is in its context window (everything it can see while it answers), and that window is a finite attention budget: it degrades as it fills. Requirements for humans are context for models. Shift left applies to prompts too: schema, grain, scope, constraints, before you ask. Look back at the three prompts above: each one carried its context, its tables and its rules before it asked for anything.

Optional

If you want the regulatory variant

The original WA3908 lab: one more ambiguous request, one more query.

"Show me our marketing compliance posture across HORIZON."

Compliance posture is the regulatory team's phrase for "how compliant are we overall", and the request assumes it is one number. The warehouse says a single blended number is dishonest: three regulators, two regions, and one market far behind the others. rfr.filings holds 112 regulatory filings (a submission to a regulator about a product, with a status such as accepted). string_agg(distinct f.regulator, ', ') lists each market's regulators in one cell.

What this checks Filing acceptance per market, with each market's region and regulators.

select f.market_code, m.region, count(*) as filings,
       round(100.0 * count(*) filter (where status = 'accepted') / count(*), 0) as pct_accepted,
       string_agg(distinct f.regulator, ', ') as regulators
from rfr.filings f join ref.markets m using (market_code) group by 1, 2 order by 1;
-- ID 14% (BPOM) · IT 65% (AAMS/EU) · JP 69% (MHLW): three regulators, two regions. Per-market is the only honest design.

Expected result ID 14% (BPOM) IT 65% (AAMS/EU) JP 69% (MHLW)

Verdict on a single "posture" number: buildable with a change one number per market, each with its regulator and its as-of date. A blended number is not as asked, because it hides the market that is far behind.
