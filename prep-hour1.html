Understand it · 1 minute

The point

Every lab today has one sentence at its centre. This is Hour 1's. Every section below ends with a "Back to the point" box that ties what you just read to it.

Code that runs without an error can still be wrong.

Students ask an AI assistant (Claude) to write a piece of database code. The code runs. No red text, no warnings. And it is still wrong: it copies people and gives some of them the wrong answer. The lab teaches one habit to catch that: check the result against answers you already know (how many rows there should be, and one person you worked out by hand). Then write those checks down as automatic tests so it stays right.

The class has a name for the bad habit: "vibe coding" means accepting code because it feels right. (Collins Dictionary made it Word of the Year in 2025.) The theme of this hour is the opposite: no vibe pipelines.

794the right answer

Italy had 794 conversions, so the finished table must have exactly 794 rows.

1,988the classic mistake

What a careless draft produces. No error. Just wrong.

trueperson 3552

The one person students check by hand. The table must agree.

4tests at the end

Automatic checks that keep it right next month.

Back to the point

If you remember one thing: "it ran" is not the same as "it is right." Everything else in this guide is detail that serves that sentence.

Understand it · 2 minutes

The story, and the PMI words

The lab is a little workplace drama in four panels. First the panels, then every company word in them, decoded.

The ask

PMI's Italy marketing team wants a list of everyone who recently switched to a smoke-free product, with a yes/no next to each: may we send them offers?

The shortcut

A colleague asks Claude to write the code. It is done in a minute and runs with no errors. "Can we ship it this afternoon?"

The catch

People in Italy have several permission slips each. The code glues all of them on, so one person appears up to four times, sometimes with different answers.

The fix

Students prove it is wrong with three checks, get Claude to fix it, then lock it with four automatic tests.

The PMI words, decoded

PMI the company

Philip Morris International, the tobacco company (Marlboro). Your students are PMI data engineers.

Only background. The data is fictional ("Project HORIZON") and safe for training.

Smoke-free products what PMI wants to sell

PMI's strategy is to move adult smokers off cigarettes onto products that do not burn tobacco. Three brands: IQOS (a device that heats tobacco instead of burning it), VEEV (an e-cigarette, a "vape") and ZYN (nicotine pouches you put under your lip).

The column product_code holds IQOS, VEEV or ZYN.

Conversion the moment PMI cares about

When a smoker switches to one of those products. "Converting" someone is the business goal.

a gym calls it a "conversion" when a free-trial visitor buys a membership.

a row in the diary table whose stage says conversion.

Lifecycle a customer's journey

Five stages, in order: registration (signs up) → trial (tries the product) → conversion (switches) → then either retention (keeps using it) or churn (gives up).

the column lifecycle_stage.

Consent permission to market

A person's yes or no to receiving marketing, given separately for each way of contacting them: email, SMS (text), push (phone app notification) and postal (paper mail). Each one is dated.

a signed permission slip. One person can sign up to four, one per channel.

the table mpl.consent_records, column marketing_allowed (true or false).

Market · IT a country

PMI calls each country a "market", with a two-letter code: IT Italy, JP Japan, ID Indonesia.

Italy only. Italian law: no marketing without permission, and no marketing at all to under-25s.

Back to the point

The business question is simple: "On the day this person switched, were we allowed to contact them?" Getting it wrong is not a typo. It means contacting people who said no, which in Italy breaks the law. That is why "it ran" is not good enough.

Understand it · 3 minutes

The tech words

Ten words, each with an everyday picture. If you already know one, skip it. The basics guide has the same words with more pictures.

Database · table where data lives

A database is a collection of tables. A table is exactly like a spreadsheet tab: named columns across the top, one record per row.

The database is called HORIZON (a Postgres database). Tables have two-part names like clr.lifecycle_events: folder clr, table lifecycle_events.

Row · "one row means…" a.k.a. the grain

The single most useful sentence about any table is "one row = one ___". Engineers call that the grain.

The table students build must be "one row = one conversion". If a person appears twice, the grain is broken.

SQL · query asking the database

SQL is the language you use to ask a database questions. One question is a query. It reads almost like English: select these columns from this table where this is true.

Students run small queries in SQLTools, a panel inside VS Code. Select the text, press Ctrl+E Ctrl+E.

count(*) how many?

"Don't show me the rows, just tell me how many there are." The single most important query in this course.

Check 1 is just count(*): should be 794.

Join gluing two tables

Put rows from two tables side by side wherever a column matches (here: the same consumer_id). The catch: a row is glued to every match. One row matched to three rows becomes three rows.

stapling a copy of a customer's order to each of their three permission slips. You now have three stapled bundles, not one.

this is the whole trap. Drawn below.

LEFT join keep everyone

A normal join drops a row that has no match. A LEFT join keeps it anyway and leaves the glued-on columns empty.

keeps the 8 people who had no permission slip yet.

NULL empty / unknown

A blank cell. Not true, not false, not zero: unknown. It silently disappears from "how many said yes?" reports.

the 8 people with no slip yet come out NULL unless the SQL says "empty means no".

dbt the build tool

dbt ("data build tool") takes a file that holds one SQL query and turns it into a saved, reusable table in the database. That file is called a model. dbt run builds it. dbt test checks it.

a recipe card (the model file) and an oven (dbt run). The dish comes out under the name on the card.

the model file is italy_conversion_events.sql; the dish is analytics.italy_conversion_events.

View a saved query

What dbt builds here. It looks and behaves like a table, but it is really a saved query that re-runs each time you read it.

students query it like any table: select count(*) from analytics.italy_conversion_events.

dbt test an automatic alarm

A query that hunts for bad rows. Finds none: PASS. Finds some: FAIL, with the count. dbt runs every test each time you type dbt test.

four tests: no duplicates, no empty ids, no empty yes/no, no under-25 marked "allowed".

The four moves students repeat all day

Students use Claude Desktop, a chat app. It cannot see the database or create files. So every step is the same four moves, and the human carries the code across:

  • 1 · Pastea prompt into Claude(the guide gives the exact text)
  • 2 · Copyits codethe Copy button on Claude's code block
  • 3 · Pasteinto a file in VS Codethe moment a human signs off
  • 4 · Rundbt or a querythe database gives the verdict

The catchphrase for move 3: "the paste is you, signing." Nothing reaches the project unless a person put it there.

Back to the point

Notice where the checking lives: not in Claude, not in dbt. dbt happily builds wrong code; Claude cannot see the data. The only one who can compare the result with a known answer is the person in the middle.

Why Claude falls into it

Understand it · 1 minute

The rule that fixes it

Each conversion must get exactly one slip. Which one? The newest slip that already existed on the day of the conversion. Engineers call this a point-in-time rule.

Three ways a draft can handle 3552, and which is right:

What the code doesConversion 9539 comes out asVerdict
glues on every slip (plain join)3 rows: true, true, false✕ one conversion became three
takes the newest slip on file, whatever its datefalse (the 19 Nov postal slip)✕ used a slip signed after the switch
takes the newest slip dated on or before 17 Novtrue (the 16 Nov push slip)✓ correct

And if there is no slip yet?

Person 4036 switched on 20 May but signed their only slip on 28 May. On the day, there was no slip, so the code finds nothing and the answer comes out NULL (empty). 8 of the 794 are like this. The rule: unknown is not permission, so no slip = false, with a comment in the code saying why.

Put together, the three rules the finished table must follow. Each comes with an answer students already know, which becomes a check in Step 2:

#RuleIn plain EnglishThe known answer
1One row per conversionno copies, nobody lost794 rows
2The slip from that daynewest slip on or before the conversion dateevent 9539 is one row, true
3No slip means nonever leave the yes/no empty0 empty rows

Walk the lab · 1 minute · class time 0:12

Opener · how the AI works

Before the lab, five minutes on what Claude actually is. It explains why Claude guesses in Step 1.

Students do

Finish this line in the chat with one word: select count(*) from ___

They see

Lots of different answers, none wrong. Then you type the same line into the Transformer Explainer (a free website that shows a small AI model choosing its next word, with a probability bar for each option).

It means

An AI language model works the same way: it scores every possible next word and picks one. Each piece it picks is a token (roughly part of a word). It writes what sounds likely, not what it has checked.

The four facts students take into the lab:

  1. It predicts the next token. It writes what sounds right. Checking is your job.
  2. It only knows what you tell it. It has never seen this database.
  3. It samples. Ask twice, get different code. So every student's draft differs.
  4. It comes in sizes. Sonnet (cheaper, $2 / $10 per million tokens in / out) does the typing; Opus (pricier, $4 / $20) does the thinking. This is "premium planning, thrifty execution": pay for the best thinker on the short, hard part (the fix plan in Step 3); let the cheaper one type the long, routine part.
Back to the point

Fact 1 and fact 2 together explain the whole lab: a model that writes what sounds right, about data it has never seen, will sometimes be confidently wrong. So someone has to check.

A good plan says three things (students tick them off):

  • one slip per conversion, dated on or before the conversion, newest first, ties broken by the higher consent_id (rules 1 and 2)
  • empty becomes false (coalesce(…, false)) with a comment (rule 3)
  • "one row per conversion" stated at the top (the grain)

If the plan says "newest consent per consumer" (no date rule), students reply: "No. It must be the newest row dated on or before each event_date. Revise the plan." That reply is them being the gate.

The correct code, read slowly

Students do not have to write this; Claude does. But you should be able to explain each part. It is three small queries stacked, like a recipe with three steps:

-- one row per Italy conversion event, with the permission in force on the day
{{ config(materialized='view', schema='analytics') }}

with events as (                                   -- PART 1: the 794 conversions
    select event_id, consumer_id, market_code, product_code, lifecycle_stage, event_date, campaign_id
    from {{ source('clr', 'lifecycle_events') }}
    where market_code = 'IT' and lifecycle_stage = 'conversion'
),
consent_on_the_day as (                            -- PART 2: one slip per conversion
    select distinct on (e.event_id) e.event_id, m.marketing_allowed
    from events e
    join {{ source('mpl', 'consent_records') }} m
      on m.consumer_id = e.consumer_id
     and m.consent_date <= e.event_date            -- only slips that existed on the day
    order by e.event_id, m.consent_date desc, m.consent_id desc
)
select e.event_id, e.consumer_id, e.market_code, e.product_code,   -- PART 3: put them together
       e.lifecycle_stage, e.event_date, e.campaign_id,
       -- no consent recorded yet = unknown, and unknown is not "allowed"
       coalesce(c.marketing_allowed, false) as marketing_allowed
from events e
left join consent_on_the_day c using (event_id)

It means

The table is right today. Next month someone edits it and the copying comes back. Nobody reruns checks by hand. A test reruns itself every build and turns it red.

A test is a query that hunts for bad rows. None found = PASS. The four:

TestHunts forGuards
unique on event_idany conversion appearing more than oncerule 1 (like check 1)
not_null on event_idrows with no conversion idevery row is a real conversion
not_null on marketing_allowedempty yes/no answersrule 3 (like check 3)
no_underage_marketing_italyany Italian aged 18 to 24 marked allowed (93 of the converters are in that age group)the law, written as a test

The first three are one-word tests listed in a settings file (schema.yml). The fourth is a hand-written query in the tests/ folder that joins a third table, clr.consumers (one row per person, with their age_band, e.g. '18-24').

Show the tests prompt to paste
The corrected model italy_conversion_events has one row per Italy conversion event. Write its tests.

File 2, tests/no_underage_marketing_italy.sql: a singular test that returns rows only when an under-25 Italian is marked as allowed. Join {{ ref('italy_conversion_events') }} m to {{ source('clr','consumers') }} c on consumer_id; return rows where c.market_code = 'IT' and c.age_band = '18-24' and m.marketing_allowed = true. {{ ref('italy_conversion_events') }} is dbt's way of saying "the model we built" (whereas source() means "a raw table").

The same four tests on the copying draft from Step 1 (real output):

FAIL 597  unique_italy_conversion_events_event_id
          Got 597 results, configured to fail if != 0
Done. PASS=3 WARN=0 ERROR=1 SKIP=0 TOTAL=4

Why 597? The unique test lists every event id that appears more than once: the people with 2, 3 or 4 slips. 195 + 207 + 195 = 597. The 197 one-slip people appear once, so they are not flagged.

The rule students must hear

If a test fails, fix the code, never the test. Deleting a failing test is like taking the battery out of a smoke alarm because it is beeping.

If a student asks…

The questions that actually come up, with answers you can say out loud.

"My draft got 794 and true on the first try. Did I do it wrong?"

No, you got a good draft. But you only know that because you counted. Your neighbour's draft looked just as good and returned 1,988. Do Steps 3 and 4 anyway: the comment and the tests are what keep it right.

"Why does a person have several consent rows?"

One per channel: email, SMS, push and postal. Each records a yes or no for that way of contacting them, with its date. 15,052 slips for 6,000 people, about 2.5 each.

"Why not just take the newest slip?"

Because it might be signed after the conversion. For 3552 the newest slip is the 19 Nov "no", but on 17 Nov they had said yes. Using it changes the answer for 13 Italians. We judge each conversion by what was true on that day.

"Why make empty into false? Isn't that hiding something?"

The opposite: empty silently drops out of every "how many are allowed?" count. Writing false with a comment says it out loud: "no permission on record, so no". In marketing law, unknown is never permission.

"Shouldn't an email campaign only look at email consent?"

Great catch, and probably yes. That is challenge 3: 45 of campaign 1's 74 conversions are allowed under "any channel", only 29 under "email only". Which rule is right is a business decision for the consent owner, not something to settle in SQL. That is exactly Hour 3's theme.

"Why does the under-25 test pass even on the bad draft?"

Because in Italy no under-25 has a "yes" slip at all: the source data already applies the law (some of their slips even say granted but have marketing_allowed = false). The test does not find a bug today. It guards against one tomorrow, if the data or the code changes.

"Why use Opus for the plan if it costs twice as much?"

The plan is a few hundred tokens, so the cost difference is pennies, and the plan is where mistakes hide. The code is long and routine, so the cheaper model types it. Premium planning, thrifty execution.

"Can't Claude just run the checks itself?"

Not in Claude Desktop: it has no connection to the database. That is on purpose today: you carry every piece of code across, so you are the one who signs. (Hour 4 shows what changes when an AI can touch the database.)

"What's the difference between a view and a table?"

A table stores rows. A view stores the query and runs it each time you read it, so it is always up to date and costs no storage. For this lab they behave the same.

"What is distinct on? I've never seen it."

A Postgres shortcut: "after sorting, keep only the first row for each event_id". Other databases do the same job with row_number(). Either is fine; what matters is that the checks pass.
