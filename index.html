The one rule

Four skills. One project. Four hours. Every hour is one Project HORIZON request taken from idea to production.

The assistant drafts. The warehouse decides. The engineer signs.

Nothing today is about whether AI is good or bad at SQL. It is very good at SQL. Today is about where accountability sits when the drafting gets fast.

The AI assistant drafts, you prove the draft against the warehouse, you sign. The four skills are Data Engineering with AI Support (WA3903), Accountability in Automation (WA3904), Cross-Functional Co-Design & Feasibility Alignment (WA3908) and Adaptive Learning Mindset (WA3906). Delivered by Accenture LearnVantage for the PMI DI&A Future Skills program.

NULLA missing value. It is neither true nor false, so a WHERE clause silently drops the rows where the test comes out unknown. Hour 2 opens with it.
ReconciliationComparing a pipeline's output to its source, per key (for example per distributor), to find rows that went missing without an error. Hour 2.
Silent suppression · silent failureA pipeline that drops or distorts rows while the job still reports success. No error, wrong number. Hour 2's missing 105 rows are a silent suppression.
Sell-through · sell-inSell-through is retail sales from the distributor or retailer to the end consumer. Sell-in is PMI's shipments to the distributor. HORIZON's rst.sell_through is weekly sell-through per distributor and product.

Conversion · lifecycle stagesIn PMI usage, conversion is an adult smoker switching to a smoke-free product. In HORIZON it is the 'conversion' value of lifecycle_stage. The journey: registration → trial → conversion → retention → churn.
Consent · marketing permissionWhether a consumer allowed marketing, and from what date: mpl.consent_records with marketing_allowed and consent_date.
Age band · under-25 ruleclr.consumers.age_band; '18-24' is the under-25 band. Marketing to under-25s is forbidden in Italy and Indonesia (0% marketing-allowed by design) and allowed in Japan.
RegulatorsMHLW (Japan's Ministry of Health, Labour and Welfare), AAMS/EU (Italy's state monopolies authority plus EU-level tobacco rules), BPOM (Indonesia's National Agency of Drug and Food Control).
KPIKey Performance Indicator: a business number, such as weekly units sold. A KPI-level check tests the number ("under-25 marketing in Italy is always zero"), not the job status.
Feasibility verdictOne of three answers to a requirement: buildable as asked · buildable with a change · not as asked, each with a number from the warehouse beside it. Hour 3's feasibility gate is one verdict per requirement.

Model tiers: Opus · Sonnet · HaikuThree price tiers of Claude. Opus is the premium model (judgment), Sonnet the thrifty one (typing), Haiku the bulk one. Same fluency, different judgment and price.
Token · context windowA token is the unit a model reads and writes, roughly three-quarters of an English word. The context window is the finite amount of text the model can see at once: everything it knows about HORIZON is what is in that window right now.
Prompt hygiene · data egressEverything you paste into an assistant leaves your data boundary. Schema, grain and scope: yes. Real rows, credentials, connection strings: never.
AgentA model, plus tools, plus a loop (think, call a tool, read the result, repeat), plus whatever permissions you gave it. Hour 4.
MCPModel Context Protocol: an open standard that lets an AI app call tools, such as a database query. The server enforces the permissions. You will see it in the instructor's Hour 4 demo.

The estate

Project HORIZON in one page

Three markets, five data assets, one Postgres database called horizon.

What it is. A fictional, training-only PMI initiative that unifies analytics, engineering and architecture around the smoke-free transformation: PMI's shift from cigarettes to products without combustion, heated tobacco (IQOS) and e-vapor (VEEV). HORIZON is invented; the transformation it stands for is not. Everything lives in one Postgres database called horizon, is transformed with dbt, queried in SQLTools and drafted with Claude.

One rule of law, three of four hours

Marketing to under-25s is forbidden in Italy and Indonesia and allowed in Japan. In the data that shows up as 0% marketing-allowed for the '18-24' age band in IT and ID, by design.

The HORIZON connection for dbt (profiles.yml)

SQLTools and dbt each keep their own copy of the connection. SQLTools saves its copy inside VS Code. dbt reads its copy from a file outside the project folder:

C:\Users\labadmin\.dbt\profiles.yml

On some VMs that file does not exist yet, and dbt debug fails until you create it. It takes two minutes, in the VS Code terminal, in the project folder (C:\Users\labadmin\Downloads\setup\horizon_dbt).

  1. See which profile name the project expects. Run Get-Content dbt_project.yml and find the line that starts profile:. Its value (for example horizon) must be the first line of profiles.yml.
  2. Create the folder and open the file with the two commands below. (If code is not recognised, use notepad "$HOME\.dbt\profiles.yml" and click Yes to create the file.)
  3. Paste the YAML below, change the first line if your profile name differs, and save.
  4. Run dbt debug again. Pre-flight step 2 shows what success looks like.

Two things break this file

Tabs (YAML needs spaces, two per level, exactly as shown) and dropping the quotes around the password (the ! needs them). And because it holds the password, it goes into the file and never into a Claude prompt: if dbt debug complains, paste the error message into Claude, not the file.

Hour 1's model reads its tables through dbt sources and builds into the analytics schema. Two small files make that work. Look in the Explorer.

A sources file in models (usually models\sources.yml; any .yml with a sources: block counts) that declares clr, mpl and rst. Without it, dbt run fails with "depends on a source named 'mpl.consent_records' which was not found" (or another source name). If it is missing, create models/sources.yml:

  - name: clr
    schema: clr
    tables:
      - name: lifecycle_events
      - name: consumers
  - name: mpl
    schema: mpl
    tables:
      - name: consent_records
  - name: rst
    schema: rst
    tables:
      - name: sell_through
      - name: distributors

A macros folder with generate_schema_name.sql. Without it, dbt glues the two schema names together and builds analytics_analytics.italy_conversion_events, so every SQLTools check in Hour 1 answers relation "analytics.italy_conversion_events" does not exist. The loop, every time

How we use Claude Desktop

Claude Desktop is a chat window. It cannot create files on your VM, run dbt or query the warehouse. That is by design today.

  1. Paste the prompt from the guide into Claude Desktop.
  2. Claude replies with SQL or YAML in a code block.
  3. You copy the code block.
  4. You paste it into a file in VS Code (or into SQLTools).
  5. You run dbt run, dbt test or the query, and read the number.
  • If Claude shows the code in a panel on the right instead of in the chat, use the Copy button at the top of that panel, or reply "Put it in a code block in the chat."
  • Opus not in the picker list? Look under More models; if it is still missing, stay on Sonnet.

The paste is you, signing. Nothing lands in the repo unless you put it there.

Read what you paste before you run it.

Fresh chat per lab

Start every hour with New chat. A fresh chat starts with an empty context window. An old conversation full of Hour 1 SQL makes Hour 2's answers worse, not better: the model attends to everything in the window, and attention is a budget.

Which model, when

Models come in tiers, and the tiers differ in price far more than in fluency; what the money buys is judgment. Default to Sonnet, the thrifty model, for drafting and implementing. For exactly one step in Hour 1 (planning the fix from facts you have proved) switch the picker to Opus, the premium model, read the plan, then switch back to Sonnet to implement it. You can change the model at any point in a conversation; the change applies from the next response. If your picker does not offer Opus, stay on Sonnet: the plan-then-implement split still works and still teaches the point.

ModelPrice per million tokens, in / outUse it for
Opus 5.5 (premium)$4 / $20judgment: reviewing, planning, deciding what to test
Sonnet 5.5 (thrifty)$2 / $10typing: drafting from a spec, implementing an approved plan, writing tests from a list
Haiku 5.5$0.10 / $0.50bulk, mechanical work with no ambiguity

Output costs five times input on every tier, and a plan is twenty lines where an implementation is two hundred. That asymmetry is why we plan on the premium model and type on the thrifty one: premium planning, thrifty execution. On a subscription the same ratio shows up as how fast you use up your session limit. (Anthropic pricing, October 2026.)

Prompt hygiene = data egress

Everything you paste into Claude leaves your data boundary. Schema, column names, grain and scope: yes. Real consumer rows, credentials, connection strings: never. No prompt in these guides contains a single real record, and none of yours should either.

Every prompt is labelled

Each prompt in the guides has the same three parts, so you always know what you are asking for and what to expect back:

  • above it, What this asks Claude to do: one plain-English sentence;
  • the prompt itself, short, with labelled lines: Context: · Task: · Tables: (schema and column names only) · Rules: · Output:, ending with "Respond in Markdown only. Do not create any file.";
  • below it, What a good answer looks like: so you can tell a good draft from a merely plausible one.
Your SQL will not match your neighbour's

The model samples its next token from a distribution of likely continuations, so one prompt gives two engineers two drafts, both fluent. That is normal. Review is about the pattern (join type, grain, NULL handling), never about matching the instructor's text. Prove with a count, not by eye.

The chat is our second screen

Room vs Warehouse

The game, and the chat house rules.

House rule for the day: the chat is our second screen. One-word answers count. "+1" to someone else's answer counts. Going off mute counts double. Nobody is graded on being right; the whole class is built on the moments where a confident answer turns out to be wrong.

Every 💬 in a lab guide is a moment to type something. Several times today you will be asked to predict a number before we run the query. The room votes in the chat; the warehouse answers. We keep score: if the room's majority is right, the room scores. If the warehouse surprises the room, the warehouse scores. We read the final score at 3:50.

The first three moments come before Hour 1 even starts.

Confession poll

Y or N: have you ever merged, shipped or forwarded code you did not fully read?

Trust meter

1 to 10: a nightly pipeline has been green for weeks. How much do you trust the number on the dashboard? We take the room's average now, and again at the end of Hour 2.

Icebreaker 1 · which face is real?

Two faces on screen. One is a photograph of a person; one was generated by a model. Type L or R. Then, one word: how did you decide? ears · teeth · background · hair · glasses · earrings · "just a feeling"

Plausible is not right

The generated face is not sloppy. It is plausible. AI-drafted SQL is exactly the same: plausible is not the same as right, and "looks fine" is not a check.

Five takeaways

These come back at 3:50 with the numbers that proved each one.

TakeawayHour
1A runnable draft is not a correct one. Give the assistant the schema, never the data. Read every join, every NULL, every grain. Prove the row count before it lands, then turn each contract into a test.1
2A green run is not a right number. Silent failures throw no errors. Reconcile to the source, prove the cause, fix the rule, leave a guard that fails loudly next time.2
3A request is intent, not a specification. Every ambiguous word is a fork in the design. Surface the assumptions, confirm feasibility against the warehouse, align first, build once.3
4New is not ready. A good demo is not pilot evidence. A capability earns each rung of the ladder, and you are the human gate in front of every one.4
5Demonstrate, don't assert. The warehouse is the arbiter. Every verdict you give today, and every one you give at PMI next week, comes with the query and the number behind it.all four
