Understand it · 1 minute

The point

Every lab today has one sentence at its centre. This is Hour 2's. Every section below ends with a "Back to the point" box that ties what you just read to it.

Green means the code ran. It does not mean the number is right.

A nightly job copies sales data into a clean table that dashboards read. Every night it finishes green: no errors, no alerts. And every night it quietly throws away one shop's sales. Nobody notices, because nothing is red. The lab teaches one habit to catch that: count what went in, count what came out, and compare, shop by shop, starting from the list of shops that should be there. Then leave an automatic alarm, and watch it ring once so you know it works.

Hour 1 was "a draft that runs can be wrong". Hour 2 is the grown-up version: a pipeline that has run green for weeks can be wrong too.

1,050should arrive

Japan's raw sales table has 1,050 rows. A correct pipeline delivers all of them.

945actually arrive

What the green pipeline delivers, every night.

105vanish silently

About €88,700 of sales, all from one online shop.

FAIL 1the alarm works

Students break the pipeline on purpose and watch their test catch it.

Back to the point

If you remember one thing: "the job is green" answers "did the code run?", not "is the number right?" Only a count against the source answers the second question.

Understand it · 2 minutes

The story, and the PMI words

The lab in four panels, then every company word in them, decoded.

The complaint

Marketing writes: "Italy's sales number on the dashboard looks too low. The pipeline has been green for weeks. Can you confirm it is fine?"

The hidden bug

Someone added one "reasonable" filter. It drops one whole shop in each market. No error. Green every night.

The hunt

Students work on Japan, the market nobody complained about. They count rows in vs out per shop and find Japan's online store has 105 in, 0 out.

The fix

Prove the cause with a count, delete one line, add a test, then break it on purpose to watch the alarm ring.

The PMI words, decoded

Distributor who sells for PMI

PMI does not sell straight to shoppers. It sells to distributors: companies that run shops or websites and sell to the public.

a farm (PMI) selling eggs through supermarkets (the distributors).

the table rst.distributors: 12 of them, 5 in Japan, 4 in Italy, 3 in Indonesia.

Channel type what kind of shop

Each distributor has one of three channels: branded_retail = PMI's own branded stores · partner_retail = other companies' shops that stock PMI products · ecommerce = online stores.

the column channel_type. Both bugs today are filters on this column.

Sell-through what the shops sold

How many units a distributor sold to customers, reported weekly. (Its opposite, sell-in, is what PMI shipped to the distributor.)

sell-in fills the shelf; sell-through empties it.

the table rst.sell_through: one row per shop, per product, per week.

Market · JP, IT a country

PMI calls each country a "market": JP Japan, IT Italy, ID Indonesia.

Marketing complained about Italy. Students fix Japan, which nobody complained about. That contrast is the lesson.

Products IQOS · VEEV · ZYN

PMI's smoke-free brands: IQOS heats tobacco, VEEV is an e-cigarette, ZYN is a nicotine pouch.

the column product_code. Not every shop sells every product.

Dashboard where the number shows up

A screen of charts that managers read. It shows whatever the clean table contains, so if rows are missing there, they are missing on the dashboard too.

Marketing only saw "Italy looks low". Nobody saw Japan at all.

Back to the point

Italy got noticed because the number looked low. Japan lost 10% of its rows and nobody blinked. "Looks fine" is not a check. A count against the source is.

Understand it · 2 minutes

The tech words

Each with an everyday picture. The basics guide covers table, row, SQL, join and dbt from scratch.

Pipeline · nightly job the conveyor belt

An automatic process that copies data from a raw table into a clean table, every night, with nobody watching.

a conveyor belt from the loading dock (raw data) to the shop floor (the dashboard).

the dbt model japan_sell_through.sql builds analytics.japan_sell_through.

"Green" job status

The job finished without an error. That is all it means. A job that drops half the data finishes just as green.

a smoke alarm with no battery: silent is not the same as safe.

green for weeks, while 105 rows were missing.

Reconciliation in vs out

Counting what went into a process and what came out, and comparing. Same idea as balancing a chequebook.

counting the eggs into the crate and out of the crate. If 10 go in and 9 come out, one broke.

Step 1: rows per distributor in the raw table vs in the pipeline.

A join with an and a hidden gate

A join glues two tables where a column matches. If the matching rule says … and something else, a row is only glued when both are true. If not, the row is dropped. No error.

the pipeline's join says "distributor matches and channel is not ecommerce".

Inner join the default

Plain join in SQL means inner join: rows with no match vanish. (A left join would keep them.)

why the online shop's sales disappear instead of showing up with blanks.

Subquery a question in brackets

A small (select …) inside a bigger query, asked again for every row. "For each shop, how many rows does it have?"

the reconciliation is built from two of these per shop.

NULL · three answers, not two the opener

Comparing with an empty value gives unknown, not true or false. A filter keeps only rows where the answer is true, so unknown rows silently vanish.

the opener: where campaign_id <> 1 returns 0 rows, not 15,523.

dbt singular test a hand-written alarm

A SQL file in the tests/ folder that lists problems. Zero rows back: PASS. Any rows back: FAIL, and the build turns red.

Step 4: a test that lists every Japan shop that lost rows.

Back to the point

Every word here is about the gap between "it ran" and "it is complete". Green, inner joins and NULL filters all drop rows without complaint. Reconciliation and tests are how you hear the complaint.

Understand it · 2 minutes

The trap, drawn

Step 2 of the pipeline (glue on the shop's details) carries one extra rule. Here is the week of 3 March going through it.

join {{ source('rst', 'distributors') }} d
    on d.distributor_id = s.distributor_id
   and d.channel_type <> 'ecommerce'   -- exclude non-store channels

Italy has a different rule doing the same damage, in a different place (the where, not the join):

where s.market_code = 'IT'
  -- limit to reportable retail channels
  and d.channel_type in ('branded_retail', 'ecommerce')

"Keep only branded and online" means partner shops are dropped: IT Partner Distributor 2, 210 rows, about €138,100. That is why Italy looked low to Marketing. Students fix Japan in the lab; Italy is Challenge 1.

Back to the point

The pipeline did exactly what its code said. That is the problem: a filter that throws rows away is valid SQL, so the job is green. Only someone who knows 1,050 should arrive can tell that 945 is wrong.

Understand it · 1 minute

Start from the list

The single most important design idea in the lab. If you check the pipeline by looking at the pipeline, the missing shop is invisible.

A shop with zero rows in the pipeline has no row to count, so a check that starts from the pipeline cannot see it. Start from the list of shops that should exist, and the missing one shows up as a 0.

Picture it

Taking the register by asking "everyone who is here, raise your hand" never finds the absent child. You have to read names off the class list.

Back to the point

This is the hour's method in one picture: compare what came out against what should exist, not against itself. A check that starts from the pipeline inherits the pipeline's blind spot.

Opener · the query that ran green

A three-minute warm-up that proves a filter can throw rows away with no error. It uses Hour 1's diary table.

Students do

Predict in the chat: how many rows does where campaign_id <> 1 ("is not 1") return? Then run three counts in SQLTools.

They see

= 1 → 74 · <> 1 → 0 (!) · is distinct from 1 → 15,523

It means

"Is NULL not equal to 1?" The database answers unknown, not true. A where keeps only true rows, so every NULL row vanishes. is distinct from treats empty as a real value and answers true.

campaign_id<> 1 saysis distinct from 1 says
1false → dropped (correct)false → dropped (correct)
NULLunknown → dropped (wrong!)true → kept ✓
Back to the point

15,523 rows lost, no error, no warning. If a filter can do that in a one-line query, it can do it inside a nightly pipeline. That is exactly what happens to Japan.

Detect · SQLTools · 9 min · class 1:19

Count in vs out

2 min read
Students do

Run two queries in SQLTools: first the totals for Japan, then the count per distributor for Japan and Italy.

They see

1,050 vs 945, then a 9-row table with two shops at 0: JP Ecommerce Distributor 3 (105 missing) and IT Partner Distributor 2 (210 missing).

It means

The total says that rows are missing. The per-shop count says which. That second query is the reconciliation.

Query 1 · "Did every Japan row reach the pipeline?"

select
  (select count(*) from rst.sell_through
    where market_code = 'JP')                         as in_source,
  (select count(*) from analytics.japan_sell_through) as in_pipeline;

Two small questions in brackets, answers side by side. 1,050 · 945 (today) 1,050 · 1,050 (after the fix)

Query 2 · the reconciliation: "For each shop, how many went in and how many came out?"

select market_code, distributor_name, in_source, in_pipeline,
       in_source - in_pipeline as missing
from (
  select d.market_code, d.distributor_name,
         (select count(*) from rst.sell_through s
           where s.distributor_id = d.distributor_id) as in_source,
         (select count(*) from analytics.japan_sell_through j
           where j.distributor_id = d.distributor_id)
       + (select count(*) from analytics.italy_sell_through i
           where i.distributor_id = d.distributor_id) as in_pipeline
  from rst.distributors d
  where d.market_code in ('JP', 'IT')
) counts
order by missing desc;

(… japan_sell_through …) + (… italy_sell_through …)…and its rows in the two clean tables. A shop is in one market only, so one side is always 0 (in_pipeline)

2a · The pipeline, line by line

LineIn plain English
from {{ source('rst','sell_through') }} sstart from the raw weekly sales, nicknamed s
join {{ source('rst','distributors') }} dglue on the shop list, nicknamed d…
on d.distributor_id = s.distributor_id…matching each sale to its shop. Fine
and d.channel_type <> 'ecommerce'…and only if the shop is not online. An extra rule with an innocent-looking comment

Show the 2b prompt (Sonnet, new chat)
Context: I am a data engineer at PMI. The dbt model below runs every night without errors.
Task: explain in plain English what this SQL does, step by step. Then list every kind of row from rst.sell_through that would NOT end up in the result, and why.
Rules: do not rewrite the SQL. Under 15 lines.
SQL:
<paste the contents of models/japan_sell_through.sql here>
Respond in Markdown only. Do not create any file.

Pasting SQL code is fine: it is code, not data. A good answer names two kinds of dropped rows: ecommerce sales (silently, because of the join's extra rule) and non-Japan rows (on purpose).

2c · The proof: "How many Japan rows does that one rule remove?"

select count(*) as rows_the_rule_removes
from rst.sell_through s
join rst.distributors d on d.distributor_id = s.distributor_id
where s.market_code = 'JP'
  and d.channel_type = 'ecommerce';

Same join, without the extra rule, counting only the online shop's Japan rows: exactly what the pipeline throws away. 105 = the gap exactly

The diagnosis, in one sentence

"The join carries a channel_type <> 'ecommerce' rule, so all 105 weekly sales rows from JP Ecommerce Distributor 3 never enter the pipeline, and nothing reports it."

Unmute

Is this a bug or a feature? Who decided online stores are "not a store"? Who should have been asked? Hold the last one: it opens Hour 3.

Back to the point

Notice the order: the data found the problem first (Step 1), the code reading found the line second, and a count confirmed it third. Claude's explanation is useful, but it is the 105 that settles it.

Be ready · 3 minutes

If a student asks…

The questions that actually come up, with answers you can say out loud.

"Why does <> 1 return 0? Surely empty is 'not 1'?"

To a person, yes. To SQL, comparing anything with NULL gives "unknown", and a where only keeps rows that are definitely true. Use is distinct from when empties should count, or add or campaign_id is null.

"Maybe excluding online sales was deliberate?"

Maybe! That is the real question. But nobody wrote it down, nobody told Marketing, and the dashboard calls itself "sell-through", not "store sell-through". A rule that changes a business number needs an owner who signs it. We treat it as a bug in the lab; in real life you ask first. That conversation is Hour 3.

"Why not just move the filter to the where?"

It would drop the same 105 rows from a different place. The problem is the rule, not where it sits.

"Isn't comparing the totals enough?"

Totals tell you that something is missing, not what. And two errors can cancel out in a total. Per shop, the missing one shows up as a clean 0.

"Why start the query from the distributors table?"

Because a shop with no rows in the pipeline has nothing to count there. Starting from the list of shops that should exist is the only way it appears, as a 0. Like taking the register from the class list rather than asking who is here.

"Why all the little (select count(*) …) brackets instead of one big join?"

Readability and safety. Each bracket asks one small question per shop, and a shop with no rows still gets a 0. A join plus group-by can quietly drop that shop again, the very thing we are hunting.

"Why break the test on purpose? It passed."

A test you have never seen fail might never fail. For example, a version that started from the pipeline's rows would pass forever. Breaking it once proves the alarm has a battery.

"My test passes but Italy is still broken. Is the test wrong?"

No, it only covers Japan. That is Challenge 2: one alarm for both markets, which fails until Italy is fixed.

"Why did nobody notice Japan?"

Nobody had an expected number to compare against. 945 looks like a perfectly normal number. Italy got noticed only because someone had a feeling it was low. Feelings are not monitoring.

"Why Sonnet all hour, not Opus?"

Today's AI jobs are routine: explain some SQL, write a test from a precise description. The one hard decision (delete the line) is made by a human. Premium models are for hard planning, as in Hour 1.
