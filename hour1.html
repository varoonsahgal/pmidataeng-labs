No vibe pipelines

A runnable draft is not a correct one. Three steps: Draft → Prove → Lock. Every prompt and query you need is on this page. Paste, do not retype.

"Vibe coding" was the Collins Dictionary Word of the Year 2025: programming by vibes, not variables. Fine for a weekend app. Not fine for a model that stamps a marketing permission on 794 real conversion events.

A runnable draft is not a correct one. The assistant drafts. The warehouse decides. You sign.

You will follow along with the instructor. Three steps: Draft → Prove → Lock. Every prompt and query you need is below. Paste, do not retype.

Premium planning, thrifty execution

One more idea runs through the hour. The cheap, fast model drafts (a draft is going to be reviewed anyway). The expensive model does the one step that is pure judgment: planning the fix from the facts you proved. Then the cheap model implements the approved plan. You spend where the thinking is, and the thing you review is a twenty-line plan, not a two-hundred-line diff (the list of changed lines).

Opener · instructor-led · 0:12

How the assistant works

Before the first prompt, six minutes on the machine you are about to hand a schema to. Nothing to install, nothing to type except one word in the chat.

Post in the chat

Finish this line and type the next word, just one: select count(*) from ___ (Do not think about it.)

The chat fills with different answers, some far more popular than others, none of them wrong. That is what a language model does on every token (a piece of a word, the unit a model reads and writes): it produces a spread of likely next tokens and picks one. The instructor then types the same fragment into the Transformer Explainer (GPT-2 small, running in your browser) so you can watch the probability bars and the temperature slider.

Four facts about the assistant
  1. It predicts the next token. Plausible is its job. Correct is yours.
  2. It only knows its window. Your prompt is its whole world: no memory of your warehouse, no rows unless you paste them (do not).
  3. It samples. Same prompt, different SQL. Prove with a count, not by eye.
  4. It comes in sizes. Premium for judgment, thrifty for typing. This lab uses both.
How this lab works

The paste is you, signing

Claude Desktop is a chat window. It cannot see your warehouse and it cannot create files on your VM. Every step uses the same loop.

  1. Paste a prompt from this guide into Claude Desktop.
  2. Claude replies with SQL or YAML in a code block. Hover over the block and click Copy.
  3. Paste it into a file in VS Code and save.
  4. Run it: dbt in the VS Code terminal for models and tests, SQLTools for queries.

The paste is you, signing. Nothing lands in the repo unless you put it there.

Why your SQL differs from your neighbour's

Your SQL will not match your neighbour's word for word. The model samples: it picks from a spread of likely next words, so one prompt gives two engineers two drafts. That is normal. The review is about the pattern (join type, grain, NULL), and the proof is a row count, never a comparison by eye.

Words you will hear

Every term used in this lab, in plain English. Each one links to the full glossary for the day.

Words you will hear Full glossary →
TermPlain English
dbt (data build tool)A tool that turns SQL SELECT statements saved as files into views or tables in the warehouse. dbt run builds them, dbt test checks them. Anything in {{ }} (config, source, ref) is an instruction to dbt, replaced before the SQL runs.
modelOne SQL SELECT saved as a .sql file in the dbt project. The file name (without .sql) is the model name.
model (dbt) vs model (AI)A dbt model is a SQL file that builds a view. An AI model is the thing behind Claude (Opus, Sonnet, Haiku). The picker next to the send button chooses the AI model.
viewA saved query that behaves like a table. Our models build as views in the analytics schema.
sourceA raw table dbt has been told about. In a model you write {{ source('clr','lifecycle_events') }} instead of clr.lifecycle_events.
schemaTwo meanings. In the database, a named folder of tables: clr, mpl, analytics. Loosely, the list of tables and columns, which is what you give Claude. schema.yml is just the dbt file that holds generic tests.
generic testA one-word check declared in schema.yml: not_null, unique, relationships (every value exists in another table), accepted_values.
singular testA SQL file in the tests/ folder that returns rows only when something is wrong. Zero rows = pass.
contractA rule the data must always obey: one row per event, marketing_allowed never NULL. A test is a contract written down.
regressionAn old bug coming back after a later change. A test that catches a regression fails the build the day it returns.
grainWhat one row represents. Here: one row per conversion event.
ledgerA table that keeps history: many rows per key over time. mpl.consent_records is a ledger, about 2.5 rows per consumer.
fan-outA join that multiplies rows because the other side has more than one match per key.
point-in-timeThe record that was in effect on the event's date, not the latest one on file.
NULL"Unknown". SQL has three truth values: true, false, unknown. A WHERE keeps only true, so a NULL vanishes from = true and from = false.
COALESCEcoalesce(a, b) returns a, unless a is NULL, then b.
DISTINCT ONPostgres: keep one row per key, the first one in the ORDER BY.
INNER vs LEFT joinINNER drops a row when the other side has no match. LEFT keeps it, with NULLs in the missing columns.
orphan rowA row whose key has no match in the table it points to.
conversionAn adult smoker switching to a smoke-free product. In HORIZON it is the 'conversion' value of lifecycle_stage (registration → trial → conversion → retention → churn).
consent / marketing permissionA consumer's yes or no to marketing: marketing_allowed, plus the consent_date it was given.
age band / under-25 ruleage_band groups consumers by age. Marketing to the '18-24' band is forbidden in Italy and Indonesia (0% allowed, by design).
SQLToolsThe VS Code extension you use to run SQL against HORIZON.
tokenThe pieces a language model reads and writes. Roughly three-quarters of an English word; a code name such as lifecycle_events splits into several. Prices are per million tokens.
context windowEverything the model can see right now: your prompt and the chat so far. It knows nothing else about HORIZON.
model tiersThe same vendor sells the model in sizes (Opus, Sonnet, Haiku). The expensive one buys judgment, not fluency; all of them type SQL fine.
prompt hygieneEverything you paste into Claude leaves your data boundary (a data egress). Schema and column names: yes. Rows, credentials, connection strings: never.

select (select count(*) from clr.lifecycle_events
         where market_code = 'IT' and lifecycle_stage = 'conversion') as source_events,
       (select count(*) from analytics.italy_conversion_events)      as model_rows;

What you should seeexpect 794 source draft returns ~1,988 A draft that joins the ledger directly fans out about 2.5x.

Check 3 · latest is not point-in-timeIf the draft takes each consumer's latest consent: how many events get a consent decided after the event?

-- 3) If the draft takes each consumer's LATEST consent: how many events get a consent decided AFTER the event?
with latest as (
  select distinct on (consumer_id) consumer_id, consent_date
  from mpl.consent_records order by consumer_id, consent_date desc)
select count(*) as conversion_events,
       count(*) filter (where e.event_date < l.consent_date) as stamped_with_future_consent
from clr.lifecycle_events e join latest l using (consumer_id)
where e.market_code = 'IT' and e.lifecycle_stage = 'conversion';
-- expect 31 of 794: a permission that did not exist yet, stamped on a historical event. Wrong for any audit.

What you should seeexpect 31 of 794 A permission that did not exist yet, stamped on a historical event. Wrong for any audit.

Check 4 · NULLPoint-in-time: how many events have no consent dated on or before the event? These become NULL.

-- 4) Point-in-time: how many events have NO consent dated on or before the event? (these become NULL)
select count(*) as events_with_no_consent_in_effect
from clr.lifecycle_events e
where e.market_code = 'IT' and e.lifecycle_stage = 'conversion'
  and not exists (select 1 from mpl.consent_records c
                  where c.consumer_id = e.consumer_id and c.consent_date <= e.event_date);
-- expect 8 of 794: with no coalesce these 8 vanish from BOTH marketing_allowed = true and = false

What you should seeexpect 8 of 794 With no coalesce, these 8 vanish from both marketing_allowed = true and = false.

If your draft already resolves consent point-in-time, your check 2 may show 794 already. Well done; the three questions below still apply to the next draft you review, and the numbers in this guide describe the most common draft.

What you should be able to say now, in one sentence each
  • Grain: the model returns ___ rows for 794 events, because ___.
  • Consent: "latest consent" is wrong because consent is point-in-time: an event must carry the permission in effect on its event_date.
  • NULL: an event with no consent dated on or before it (8 of the 794) has marketing_allowed = NULL, which silently drops out of = true and = false filters. Unknown is not "allowed".

Takeaway #1

A runnable draft is not a correct one

A runnable draft is not a correct one. Give the assistant the schema, never the data. Read every join, every NULL, every grain. Prove the row count against the warehouse before it lands, then turn each contract into a test. No vibe pipelines.

Premium planning, thrifty execution. Spend the expensive model on judgment (the plan) and the cheap one on typing (the draft, the implementation, the tests). Review the plan; it is shorter than the diff and it is where the mistakes are.
