The big picture · read this first

The mission in 60 seconds

What we are building, why it matters, and the two numbers that decide whether we got it right.

The situation

PMI Italy ran the Autumn Conversion Push, an email campaign to get people to switch to a smoke-free product (a "conversion"). Now Marketing wants to report how well it worked, comparing the campaign's conversions with all the others. But a campaign can only take credit for people it was allowed to contact, and in Italy that means people who had given permission on the day. A conversion from someone who said no, or who never said yes, is not a win. It is a problem for Legal.

So before anyone counts results, every conversion needs one flag.

Your mission

Build one table that lists every Italy conversion and answers one yes/no question for each:

"On the day this person converted, were we allowed to market to them?"

When you finish, the table will look like this (real rows from the finished table):

The two numbers you will hear all hour

The right answer794

Italy had 794 conversions. One row per conversion means the finished table must have exactly 794 rows. Not more, not fewer.

The classic mistake1,988

A careless draft copies each conversion once for every permission slip that person has, and ends up with 1,988 rows. No error message. Just wrong.

You will see exactly where both numbers come from in Understand the data.

Opener · instructor-led · 0:12

How the assistant works

Six minutes on the machine that will write your first draft. Nothing to install.

Post in the chat

Finish this line with the next word, just one: select count(*) from ___ (Do not think about it.)

The chat fills with different answers, and none of them is wrong. A language model does the same thing: it looks at the words so far, scores every possible next word, and picks one. Each piece it picks is called a token (roughly part of a word). The instructor types the same line into the Transformer Explainer so you can watch those scores live.

Four facts that explain this whole lab
  1. It predicts the next token. It writes what sounds right. Checking it is right is your job.
  2. It only knows what you tell it. It has never seen our warehouse. It only knows the table names you paste in.
  3. It samples. Same question, different SQL each time. Your draft will differ from your neighbour's.
  4. It comes in sizes. A cheaper model for typing, a more expensive one for thinking. This lab uses both.
How this lab works

The paste is you, signing

Claude Desktop is a chat window. It cannot see the database or create files. So every step is the same four moves.

  1. Paste a prompt from this page into Claude Desktop.
  2. Copy the code Claude replies with (the Copy button on its code block).
  3. Paste it into a file in VS Code and save.
  4. Run it: dbt in the VS Code terminal, or a query in SQLTools.

Nothing reaches the project unless you paste it there. That paste is your signature.

AI tidbit · what a token costs

The Step 1 prompt is about 850 characters. At roughly 4 characters per token that is a few hundred tokens, so at Sonnet's $2 per million it costs about a twentieth of a cent, and the whole draft well under one cent. Cost is not why we check the draft. Correctness is.

To see text split into tokens, paste a line of SQL into Tiktokenizer. It shows OpenAI's tokenizers (Claude splits text a little differently), but the idea is the same: words, column names and symbols break into pieces.

Prices: the table above. "4 characters per token" is a rule of thumb for English, not an exact figure.

Prompt hygiene: what may go into Claude

Yes: table names and column names. Never: real rows of data, passwords, connection details. Every prompt on this page follows that rule.

Before the first query

SQL in five words

Every query in this lab is built from these five words. Each query below is also translated line by line.

select"Show me these columns."select event_id, event_date
from"…from this table."from clr.lifecycle_events
where"…but only the rows that match."where market_code = 'IT'
count(*)"Don't show the rows. Just tell me how many."select count(*) from …
join"Glue two tables together, row to row, wherever a column matches."join … on c.consumer_id = e.consumer_id
Two more things you will see
  • Short names. from clr.lifecycle_events e gives the table the nickname e, so e.event_date means "the event_date column of that table".
  • NULL means "empty, unknown". It is not true and not false. SQL quietly skips it when you ask for = true or = false.

So which slip counts?

Each conversion must get exactly one slip. The right one is the newest slip that already existed on the day of the conversion. A slip signed later did not exist yet, so it cannot count. For 3552, who converted on 17 Nov:

Three ways an AI draft might attach a slip, and what each one does to 3552:

And if there is no slip yet?

Customer 4036 converted on 20 May 2024. Their only slip was signed on 28 May, eight days later. On the conversion day there was no slip at all.

AI tidbit · why Claude guesses instead of asking

Why doesn't Claude stop and ask "which consent record?" A 2025 paper, Why Language Models Hallucinate, compares models to students facing hard exam questions: when unsure, they guess, because training and scoring usually reward a confident guess over "I don't know". So a vague word in a prompt rarely comes back as a question. It comes back as a plausible answer.

Source: Kalai, Nachum, Vempala and Zhang (2025), arXiv:2509.04664.

AI tidbit · why your SQL differs from your neighbour's

At every step the model has a list of possible next tokens, each with a probability. It does not always take the top one: it samples, with a little randomness, so the same prompt can come back as different SQL. A setting called temperature controls how adventurous that pick is, and the Transformer Explainer has a slider for it. That is why this lab never asks "did you get the same SQL?", only "does it pass the same checks?"

Sources: Anthropic's glossary (temperature); the Transformer Explainer paper.

-- italy_conversion_events: one row per Italy conversion event,
-- with the marketing permission in force on the event date.
{{ config(materialized='view', schema='analytics') }}

with events as (
    select event_id, consumer_id, market_code, product_code, lifecycle_stage, event_date, campaign_id
    from {{ source('clr', 'lifecycle_events') }}
    where market_code = 'IT'
      and lifecycle_stage = 'conversion'
),

consent_on_the_day as (
    -- one row per event: the newest consent dated on or before the event
    select distinct on (e.event_id)
        e.event_id,
        m.marketing_allowed
    from events e
    join {{ source('mpl', 'consent_records') }} m
        on m.consumer_id = e.consumer_id
       and m.consent_date <= e.event_date
    order by e.event_id, m.consent_date desc, m.consent_id desc
)

select
    e.event_id,
    e.consumer_id,
    e.market_code,
    e.product_code,
    e.lifecycle_stage,
    e.event_date,
    e.campaign_id,
    -- no consent recorded yet = unknown, and unknown is not "allowed"
    coalesce(c.marketing_allowed, false) as marketing_allowed
from events e
left join consent_on_the_day c using (event_id)
with events as ( … )Part 1. Make a temporary list called events: the 794 Italy conversions.
consent_on_the_day as ( …Part 2. A second temporary list: one slip for each conversion.
join … on m.consumer_id = e.consumer_id and m.consent_date <= e.event_dateGlue on only the slips that already existed on the conversion day (rule 2). For 3552: email and push, not postal.
order by e.event_id, m.consent_date desc, m.consent_id descSort each person's slips newest first, using the tie-breaker. For 3552: push (16 Nov) comes first.

Why this step

The table is right today. Next month someone edits the SQL, or asks an AI to "tidy it up", and the copying comes back. Nobody re-runs your checks by hand. A dbt test is a check that runs automatically every time and turns the build red if a rule breaks.

What a dbt test is, in one line

A test is a query that looks for broken rows. If it finds none, the test passes. Here are our four, and the check or rule each one automates:

TestWhat it looks forProtects
unique on event_idany conversion that appears more than oncerule 1, like Check 1 (no copies)
not_null on event_idrows with no conversion idevery row is a real conversion
not_null on marketing_allowedempty yes/no answersrule 3, like Check 3
no_underage_marketing_italyany Italian aged 18 to 24 marked as allowed (Italy forbids marketing to under-25s; 93 of our converters are in that age group)the law, written as a test

The first three are one-word tests that dbt already knows. You list them in a file called schema.yml. The fourth is a small SQL file of our own in the tests folder.
