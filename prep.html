The day · 2 minutes

Four hours, four points

A 4-hour class for PMI data engineers, built from four 1-hour courses. Each hour has one theme and one point. Students do a hands-on lab in each.

Hour 1 · WA3903 · 0:12–1:05No vibe pipelinesCode that runs without an error can still be wrong.Claude drafts a table; students prove it wrong with three known answers (794 rows, not 1,988), fix it, lock it with tests.Hour 1 prep guide → Hour 2 · WA3904 · 1:08–1:55Green ≠ rightA pipeline that finishes "green" can still be losing data.A nightly job silently drops one shop's sales. Students count rows in vs out, find the one bad line, fix it, and leave an alarm.Hour 2 prep guide → Hour 3 · WA3908 · 2:07–2:57Shift leftAsk the questions before anyone builds.Marketing asks for "real-time dashboards across all markets". Students build nothing: they find the hidden guesses and prove two of them impossible with data.Hour 3 prep guide → Hour 4 · WA3906 · 3:00–4:00You are the gateNew is not ready. Notice the arc: Hours 1 and 2 catch problems after building (a wrong draft, a lying pipeline). Hour 3 asks how both could have been caught before. Hour 4 applies everything to the next shiny AI tool.

Back to the point

All four hours teach one habit from different angles: do not trust a result because it looks finished. Check it with a number you can explain.

The day · 2 minutes

The company and the data

The students work at PMI. The data is a made-up but realistic warehouse called Project HORIZON. Here is what lives where.

PMI (Philip Morris International) is the tobacco company behind Marlboro. Its strategy is to move adult smokers onto smoke-free products that do not burn tobacco: IQOS (heats tobacco), VEEV (e-cigarette) and ZYN (nicotine pouches). Your students are PMI's data engineers: the people who build the tables and pipelines that the business reads.

Project HORIZON is a fictional training database covering three countries (PMI says "markets"): JP Japan, IT Italy, ID Indonesia. Each has its own regulator and its own laws. The big one: marketing to people aged 18 to 24 is forbidden in Italy and Indonesia, allowed in Japan.

The database is organised into folders (database people say schemas). The short names look cryptic; here they are decoded:

FolderStands forWhat is in it (one row = …)Hours

mplMarketing Permission Ledgerconsent_records (one row = a person's yes/no to one contact channel, dated)1, 3, 4
rstRetail Sell-Throughdistributors (one row = a company that sells PMI products) and sell_through (one row = one distributor, one product, one week of sales)2, 3, 4

Back to the point

The data is not broken anywhere. Every trap today comes from an assumption about the data ("one consent per person", "online stores are not stores", "real-time is possible"). Knowing what one row means is half of every lab.

The tech · 2 minutes

Tables and SQL

If you can read a spreadsheet, you can read a table. SQL is how you ask it questions.

A query asks that table a question. It reads almost like English:

select distributor_name         -- show me this column
from rst.distributors            -- from this table
where channel_type = 'ecommerce' -- but only rows where this is true
-- answer: JP Ecommerce Distributor 3, IT Ecommerce Distributor 3, ID Ecommerce Distributor 3

The SQL words you will meet today, all of them:

WordMeansExample
select … from …show these columns from this tableselect event_id from clr.lifecycle_events
wherekeep only rows where this is truewhere market_code = 'IT'
count(*)don't show rows, just say how manyselect count(*) from … → 794
sum · avgadd up · averageavg(units_sold) → 277
group byone answer per group instead of one overallgroup by market_code → one row per country
e.event_ida nickname: "event_id from the table nicknamed e"from clr.lifecycle_events e
join … onglue two tables together where a column matchesdrawn in the next section
( select … )a small question inside a bigger one (a subquery)count rows per distributor, Hour 2
filter (where …)count only some rows, next to the full count"249 people, 0 of them allowed"
exists ( … )"is there at least one matching row?" yes/nodoes this person have any "yes" slip?
Back to the point

The most important query all day is the humblest one: count(*). Most of the "checks" in every lab are a count compared with a number you already know.

The tech · 2 minutes

Joins, drawn

A join glues rows from two tables together wherever a column matches. Two facts about joins cause the problems in Hours 1 and 2.

Hour 2 adds one twist: a join can carry extra conditions, on d.distributor_id = s.distributor_id and d.channel_type <> 'ecommerce'. A row is kept only when both are true, so every online-store sale silently fails the second condition and vanishes (fact 2).

Back to the point

A join can add rows (fan-out) or remove rows (no match) without any error. That is why "rows in vs rows out" is the first check in both coding labs.

The tech · 1 minute

NULL, drawn

NULL is an empty cell: not true, not false, not zero. It means "unknown", and it quietly breaks filters.

The Hour 2 opener in one table. The diary has 15,597 rows: 74 with campaign_id = 1 and 15,523 empty (NULL). How many rows are "not campaign 1"?

QueryAnswerWhy
where campaign_id = 174as expected
where campaign_id <> 10"is NULL different from 1?" → unknown. where keeps only true, so every NULL row is dropped
where campaign_id is distinct from 115,523treats empty as a real value: the right answer

Two more NULL tools: is null finds empty cells (never = null, which matches nothing), and coalesce(x, false) means "use x, but if it is empty use false". Hour 1 uses it for "no permission slip means no".

Back to the point

NULL is how wrong numbers hide in plain sight: a filter returns 0 instead of 15,523, and nothing turns red.

The tech · 2 minutes

dbt in one picture

dbt ("data build tool") is how data engineers turn SQL queries into saved tables, and check them. Hours 1 and 2 use it; Hours 3 and 4 do not.

  • 1 · The modela .sql fileone select query, saved as e.g. japan_sell_through.sql
  • 2 · dbt runbuilds itsends the query to the database and saves the result
  • 3 · The viewa "table" you can querynamed after the file, in the analytics folder
  • 4 · dbt testchecks itruns every test: PASS or FAIL with a count

Model the recipe card

A file holding one select. Its file name becomes the table name.

a recipe card; dbt run is the oven.

View a saved query

What dbt builds here. Reads like a table; really a saved query that re-runs each time.

{{ source('rst','sell_through') }} raw table

dbt's way of writing rst.sell_through: "the raw table called…". The {{ }} are dbt's fill-in-the-blank brackets.

{{ ref('japan_sell_through') }} another model

"The table built from that model file". Used in tests to point at what we built.

{{ config(…) }} settings line

The first line of a model: "save this as a view in the analytics folder".

Test an alarm

A query that hunts for bad rows. Finds none: PASS. Finds some: FAIL with the count. One-word tests (unique, not_null) are listed in schema.yml; custom ones are .sql files in tests/.

a smoke alarm: silent when all is well, loud the moment it is not.

dbt run --select italy_conversion_events    # build one model
dbt test --select italy_conversion_events   # run its tests
Done. PASS=4 WARN=0 ERROR=0 SKIP=0 TOTAL=4   # what success looks like
Back to the point

dbt run going green proves only that the SQL is valid. dbt never checks whether the numbers are right. Only tests do that, and only for the rules someone wrote down.

The tech · 2 minutes

The AI words

Enough to explain the opener in Hour 1 and the agent in Hour 4.

Language model LLM

The engine inside Claude. It has read a vast amount of text and writes by predicting what comes next.

a phone's autocomplete, scaled up enormously.

Token a piece of a word

Models read and write in chunks of roughly ¾ of a word (about 4 characters). Prices and memory limits are counted in tokens.

Next-token prediction how it writes

At every step it scores all possible next tokens and picks one. It writes what sounds likely, not what it has checked. Shown live with the Transformer Explainer.

Sonnet · Opus · Haiku model sizes

Claude comes in sizes. Per million tokens (in / out): Opus $4 / $20 (best thinker), Sonnet $2 / $10 (strong, cheaper), Haiku $0.10 / $0.50 (bulk work).

"premium planning, thrifty execution": Opus writes the short plan, Sonnet types the long code.

Context window its working memory

Everything the model can "see" at once: instructions, chat, pasted text. Large ones hold about 200,000 tokens, and quality drops as it fills ("context rot").

Agent · tool call AI that does things

An agent can ask for actions ("run this SQL"), read the result and continue. Each request is a tool call.

Hour 4. Today the "tool" is the student, who runs the SQL by hand.

MCP Model Context Protocol

A standard plug that connects an AI app to a tool such as a database. The permissions live in the plug, not in the prompt.

a USB-C port for AI tools.

Automation bias a human habit

Trusting a number more because a machine produced it. Every lab is a small cure for it.

Back to the point

A model that writes what sounds right, about data it has never seen, will sometimes be confidently wrong. That single fact is why the human signs.

Reference · the morning of class

Before class, on your Mac

Your Mac runs a local copy of the HORIZON warehouse in Docker, identical to the students' data. Five commands make sure it matches what the guides say.

  1. Start Docker Desktop, then the warehouse 
    cd ~/pmidataeng/horizon-warehouse
make up

    warehouse ready: localhost:5432 / horizon / postgres

  2. Check every number in the guides 
    make verify

    Prints the ground-truth numbers (794, 1,988, 105, 277…). Compare them with the table above.

  3. Reset to the class starting state 
    make plant

    …|945 Removes any lab files you made and re-plants the Hour 2 bug.

  4. Prove the Hour 4 database door (MCP) 
    make demo-prep

    Checks the numbers, the read-only connection (277, then the DELETE refused with READONLY_VIOLATION) and prints the on-stage checklist.

  5. Restart Claude Desktop

    Fully quit (Cmd+Q) and reopen, so it loads the database connector for the Hour 4 demo.
