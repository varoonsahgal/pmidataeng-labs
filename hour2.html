Hour 2 · Accountability in Automation (WA3904)

Green ≠ right

The nightly job has been green for weeks. No error, no alert, a plausible row count. And one distributor's sales have been missing from every dashboard since the day the filter shipped.

Automation does the work. You own the outcome.

The loop for this hour: Detect → Diagnose → Correct → Prevent.

Hands-on: you will harden the Japan pipeline with the instructor. Italy is the story; Japan is the one nobody noticed.

How this lab works with Claude Desktop

Claude Desktop is a chat window. It cannot create or edit files on your VM. The loop all hour is: paste a prompt into Claude Desktop → Claude replies with SQL in a code block → you copy it → you paste it into a file in VS Code → you run dbt or SQLTools and read the number. The paste is you, signing. Nothing lands in the repo unless you put it there.

Model: Sonnet all hour

Stay on Sonnet for the whole hour (the model picker is next to the Send button). Hour 1's "premium planning" is for judgment with a long implementation behind it. Today's fix is one line and the tests come from a precise list: that is typing, so the thrifty model is the right tool.

Prompt hygiene, once

Everything you paste into Claude leaves the VM. Schema and column names: yes. Real rows, passwords, connection strings: never.

Words you will hear

Every term this hour uses, in plain English. Each one links to its entry in the glossary.

Words you will hear Full glossary →
TermPlain English
Sell-throughRetail sales from a distributor or retailer to the end consumer. The opposite of sell-in, which is PMI's shipments to the distributor. In HORIZON, rst.sell_through holds one row per distributor, product and week, and every sale_date is a Monday.
Distributor · channel typeThe trading partner that sells to consumers. Each one has a channel_type: branded_retail (PMI's own stores), partner_retail (third-party retail) or ecommerce. Both bugs today are channel filters that drop a whole distributor.
dbtData build tool. A SQL SELECT saved as a file is a model; dbt run builds it in the warehouse as a view; dbt test checks it. A source is a raw table you declare once and then write as {{ source('rst','sell_through') }}.
ViewA saved query that behaves like a table. Nothing is copied; the SELECT runs when you read it. All HORIZON models are views in the analytics schema.
Source vs stagedSource is the raw table the feed loads (rst.sell_through). Staged is the cleaned, scoped copy the pipeline builds from it (analytics.japan_sell_through). A healthy pipeline can explain every row that is in one and not the other.
GrainWhat one row represents. Here: one distributor, one product, one week.
ReconciliationComparing the pipeline's output with its source, per key (here per distributor), to find rows that vanished. The check that catches what a green job status cannot.
Silent suppressionRows removed by a rule that throws no error. The job is green, the row count looks plausible, and one distributor's sales are gone.
Threshold driftAn alert threshold set once and never recalibrated, so it no longer matches the data and never fires. A monitor that has never fired has never been tested either.
Anomaly thresholdA tolerance band around a series' own average. A week outside the band is flagged. The band has to be calibrated against the real spread, not guessed.
NULL · three-valued logicA SQL comparison returns true, false or unknown. NULL <> 1 is unknown. A WHERE clause keeps only true, so NULL rows silently drop out of = x and <> x.
IS DISTINCT FROMA comparison that treats NULL as a value. campaign_id is distinct from 1 is true for NULL rows; campaign_id <> 1 is not.
COALESCEReplaces NULL with a default: coalesce(n_staged, 0) turns "no staged rows found" into the number 0 so you can subtract it.
CTECommon Table Expression: a WITH clause that names a sub-query at the top of a statement so the main SELECT below can use it like a table. Used in the stretch to hold each series' average.
INNER vs LEFT joinINNER keeps only rows that match on both sides. LEFT keeps every row from the left table and fills the right side with NULL when nothing matches. A reconciliation must be LEFT (or FULL), or it hides the very distributor you are hunting.
Singular testA dbt test written as a plain SQL file in tests/. It returns rows only on failure; zero rows means PASS. Written with {{ ref('model') }} and {{ source(...) }}, no trailing semicolon.
KPI · KPI-level checkKey Performance Indicator, a business number. A KPI-level check guards the number itself ("under-25 marketing in Italy is always zero": marketing to the '18-24' age band is forbidden by law in Italy and Indonesia, so the count of under-25 consumers with marketing_allowed must be 0), not the job status.
Automation biasAccepting a confident, specific suggestion from a tool more readily than the same suggestion from a colleague, and checking it less.
Human approval gateA step where a person must say yes before an automated action (a delete, an overwrite, a threshold change) takes effect.
SQLToolsThe VS Code extension you use to run SQL against HORIZON. Paste a query into your SQLTools tab (you open it in Before you start), select it, and press Ctrl+E twice (or click Run on active connection).
Model tiers · SonnetClaude comes in three price tiers: Opus (premium, for judgment), Sonnet (thrifty, for typing) and Haiku (bulk). This hour stays on Sonnet. You change it with the model picker next to the Send button; the change applies from the next reply.

Predict in the chat

clr.lifecycle_events has 15,597 rows. 74 of them have campaign_id = 1. How many rows does this return? 15,523 · 15,597 · 74 · 0 · something else

select count(*) from clr.lifecycle_events where campaign_id = 1;

-- 0  (not 15,523)

What a good answer looks likeexpect 74 <> 1 returns 0, not 15,523

Run both in your SQLTools tab. 0. Every row that is not campaign 1 has campaign_id = NULL, and NULL <> 1 is unknown, not true. A WHERE clause keeps only true. No error, no warning, a perfectly green run, and a number that is wrong by 15,523.

select count(*) from clr.lifecycle_events where campaign_id is distinct from 1;
-- 15,523  (the fix: IS DISTINCT FROM treats NULL as a value)

What a good answer looks like15,523 IS DISTINCT FROM treats NULL as a value.

Keep that feeling; it is the whole hour. A green run tells you the code executed. It tells you nothing about whether the number is right.

Four ways green hides wrong

The instructor will walk through these; the lab is about the first one, the stretch is about the second and third.

PatternWhat it looks likeWhat would tell you
Silent suppressionA rule drops "bad" rows. The job is green, the count is plausible.A reconciliation to the source, per distributor.
Threshold driftThe anomaly alert was set a year ago and has never fired.Look at the real spread; was the threshold ever calibrated against it?

Context: I am a data engineer at PMI on Project HORIZON (Postgres). I am checking whether two dbt pipelines silently drop rows.
Task: write ONE SQL query that compares source row counts with staged row counts per distributor, for market_code in ('IT','JP').
Tables:
- source: rst.sell_through (record_id, sale_date, market_code, distributor_id, product_code, units_sold, gross_revenue_eur)
- staged: analytics.italy_sell_through and analytics.japan_sell_through (same columns, plus distributor_name, channel_type)
- rst.distributors (distributor_id, distributor_name, market_code, channel_type)
Rules: every distributor must appear even if it has zero staged rows.
Show market_code, distributor_name, channel_type, the source count, the staged count and the gap. Sort by the gap, largest first.
Do not run anything.
Output: the SQL in one code block, then two sentences on which join type you chose and why.
Respond in Markdown only. Do not create any file.

What a good answer looks likeOne SELECT built from two count subqueries (source rows per distributor; staged rows per distributor from both models, combined with union all), a LEFT join from the source side, coalesce(n_staged, 0), a dropped column, sorted by dropped desc. Claude says it chose LEFT so that a distributor with no staged rows still shows up.

Read it before you run it

Three questions:

CheckWhy it matters
Is the join from source counts to staged counts a LEFT (or FULL) join?With an INNER join, a distributor with zero staged rows simply disappears from the result and you conclude "all fine". The reconciliation would have the same bug as the pipeline.
Is the staged count wrapped in coalesce(..., 0)?Without it the gap for a missing distributor is 210 - NULL = NULL, which sorts nowhere and reads as nothing.
Does it read both staged models?Italy is the story, Japan is the lab. You want both in one result.
If any check fails

Reply in the same chat: Change the join between the source counts and the staged counts to a LEFT join from the source side, and wrap the staged count in coalesce(..., 0). Then read it again.

Copy the SQL into your SQLTools tab and run it. Different-but-valid SQL is normal; what matters is the join type and the numbers. If yours looks very different, use the reference version:

select d.market_code, d.distributor_name, d.channel_type,
       src.n_source,
       coalesce(stg.n_staged, 0)                 as n_staged,
       src.n_source - coalesce(stg.n_staged, 0)  as dropped
from (
    select distributor_id, count(*) as n_source
    from rst.sell_through where market_code in ('IT','JP') group by distributor_id
) src
left join (
    select distributor_id, count(*) as n_staged from analytics.italy_sell_through group by distributor_id
    union all
    select distributor_id, count(*) from analytics.japan_sell_through group by distributor_id
) stg using (distributor_id)
join rst.distributors d using (distributor_id)
order by dropped desc, d.market_code, d.distributor_name;
-- expect 9 rows; the top two have dropped = 210 (IT) and 105 (JP); the other seven have dropped = 0

Detect told you which distributor. Diagnose is finding why, and proving it with a count.

In VS Code, open models/japan_sell_through.sql. Read the from / join block. Read the join condition, not just the key:

join {{ source('rst', 'distributors') }} d
    on d.distributor_id = s.distributor_id
   and d.channel_type <> 'ecommerce'   -- exclude non-store channels

A plausible-looking scoping rule with an innocent comment. The join matches on the distributor key and on a channel rule, so every row of the one ecommerce distributor in Japan fails the join and never enters the model. Prove it in SQLTools:

select count(*) as suppressed_rows
from rst.sell_through s
join rst.distributors d using (distributor_id)
where s.market_code = 'JP'
  and d.distributor_id = 3                -- JP Ecommerce Distributor 3, from Detect
  and d.channel_type = 'ecommerce';       -- the channel the join silently excludes
-- expect 105: exactly the gap the reconciliation found

What a good answer looks likeexpect 105 Exactly the gap the reconciliation found.

Reference version, if yours did not pass the read-through:

-- Guard 1: row-count reconciliation. Fails if ANY Japan distributor has fewer staged rows than source rows.
select d.distributor_id, d.distributor_name, src.n_source, coalesce(stg.n_staged, 0) as n_staged
from (
    select distributor_id, count(*) as n_source
    from {{ source('rst', 'sell_through') }} where market_code = 'JP' group by distributor_id
) src
left join (
    select distributor_id, count(*) as n_staged
    from {{ ref('japan_sell_through') }} group by distributor_id
) stg using (distributor_id)
join {{ source('rst', 'distributors') }} d using (distributor_id)
where coalesce(stg.n_staged, 0) < src.n_source

What a good answer looks likeA CTE (a WITH clause: a named sub-query you define at the top and use below) with avg(units_sold) per distributor and product, a join back on both keys, a where with two factors. Claude usually proposes something like 0.5x and 2x. Confident, specific, and uncalibrated.

Look at Japan's real spread first (SQLTools, on the fixed model):

select distributor_id, product_code, min(units_sold), round(avg(units_sold)) as avg_units, max(units_sold),
       round(max(units_sold)::numeric / avg(units_sold), 2) as max_over_avg,
       round(min(units_sold)::numeric / avg(units_sold), 2) as min_over_avg
from analytics.japan_sell_through group by 1, 2 order by 1, 2;

Automation bias

A threshold copied from the assistant without this check is calibrated by luck. That is automation bias: a confident, specific number from a tool gets checked less than the same number from a colleague. The habit that protects you is boring: look at the real distribution before you accept any number the model proposes.

Takeaway #2

A green run is not a right number

Silent suppression, threshold drift and over-trust in AI output throw no errors. Detect with a reconciliation to the source. Diagnose by proving the cause against the warehouse. Correct the rule. Prevent with a guard that fails loudly next time, and watch it fail once so you know it works. Green ≠ right.
