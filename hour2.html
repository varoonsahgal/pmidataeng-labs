The big picture · read this first

The mission in 60 seconds

What is going on, what you will prove, and the three numbers that tell the whole story.

The situation

PMI does not sell straight to shoppers. It sells through distributors: companies that run PMI's own stores, partner shops or online stores. Every week, each distributor reports how many units of each product it sold. That is called sell-through.

Every night an automatic job (a pipeline) copies those weekly sales from the raw table into a clean table that the dashboards read. The job has finished green (successful, no errors) every night for weeks.

Then Marketing writes: "Italy's sales number looks too low. Can you confirm it is fine?"

Your mission

Prove whether the pipeline's numbers match the raw data. If rows are missing, find out which ones and why, fix it, and leave an alarm so it can never happen silently again.

You will do it hands-on for Japan: the market nobody complained about.

Here is one real week from the raw Japan sales: Monday 3 March 2025. Ten rows went in. Look at what came out.

The numbers that tell the whole story

Should arrive1,050

Japan's raw table has 1,050 rows of weekly sales. A correct pipeline delivers all of them.

Actually arrive945

The pipeline delivers 945. 105 rows (about €88,700 of sales) vanish every night, with a green job status.

You will find out exactly where the 105 go in Step 2.

A three-query warm-up that shows the whole hour in miniature: no error, and a wrong number.

Remember the diary table from Hour 1, clr.lifecycle_events? It has a column campaign_id: which marketing campaign led to that event. Only some events came from a campaign. The rest have no value there: NULL.

"How many events are not from campaign 1?"

select count(*) from clr.lifecycle_events where campaign_id = 1;
select count(*) from clr.lifecycle_events where campaign_id <> 1;
select count(*) from clr.lifecycle_events where campaign_id is distinct from 1;
Line by line
where campaign_id = 1Count the rows from campaign 1.
where campaign_id <> 1Count the rows that are "not 1". (<> means "is not equal to".)

Why: the rule SQL follows

A where keeps a row only when its condition is true. Asking "is empty not 1?" does not give true. It gives unknown, so the row is thrown away:

campaign_id = 1 <> 1false: row dropped (correct, it is 1)
campaign_id = NULL <> 1unknown: row dropped (wrong! empty is not 1)
campaign_id = NULL is distinct from 1true: row kept ✓

What it means for this hour: a filter can quietly throw rows away and the job still finishes green. That is exactly what is happening to Japan's sales. Keep this feeling: it is the whole hour.

Understand the data · 5-minute read

Two tables and one pipeline

What the raw data looks like, what the pipeline does with it, and why 1,050 is the right number.

Goal: all 1,050 Japan rows arrive›The data›1 Detect›2 Diagnose›3 Correct›4 Prevent

Table 1 · rst.distributors: who sells for PMI

One row = one distributor. Each has a channel: how it sells to shoppers. Here is every distributor in Japan and Italy:

Table 2 · rst.sell_through: the weekly sales

One row = one distributor, one product, one week. Every week starts on a Monday, and the data covers 105 weeks (1 Jan 2024 to 29 Dec 2025). You saw one Japan week in the mission: 10 rows, because Japan's 5 distributors sell 10 distributor-and-product combinations between them.

The pipeline: models/japan_sell_through.sql

In plain English, the nightly Japan pipeline does three things:

  1. Take every row of rst.sell_through…
  2. …glue on the distributor's name and channel from rst.distributors (a join)…
  3. …and keep only Japan. The result is saved as analytics.japan_sell_through.

Somewhere in that SQL is one extra rule that someone thought was reasonable. You will find it from the data first, then in the code.

2Detect · query 2 · the reconciliation

"For each distributor: how many rows went in, and how many came out?"

Why we run it

It points at the exact distributor that went missing. We check Japan and Italy together, because Italy is the market Marketing complained about.

Run this 
select market_code, distributor_name, in_source, in_pipeline,
       in_source - in_pipeline as missing

  where d.market_code in ('JP', 'IT')

What it means for the goal: two distributors are missing completely, one in each market. Italy's partner shops (210 rows, about €138,100 of sales) explain Marketing's complaint. Japan's online store (105 rows, about €88,700) is the one nobody noticed.

Why "start from the list" matters

Suppose you counted the other way round, starting from the pipeline's own rows. Distributor 3 has no rows there, so it would not appear at all: you would see four happy Japan distributors and conclude "all fine". A check that starts from the pipeline inherits the pipeline's blind spot. Start from what should exist, and a missing distributor shows up as a 0.

Why this step

The fix lives in one file and one head: yours. Next quarter someone adds another "reasonable" filter, and nobody re-runs your queries by hand. A dbt test runs every time the pipeline is built and turns it red the day rows go missing.

4a · Ask Sonnet to write the alarm

A dbt test is a query that looks for problems: if it finds rows, the test fails. Our test is Step 1's query 2, for Japan, keeping only distributors that came up short.

Takeaway #2

A green run is not a right number

Green means the code ran, not that the number is right. Detect with a count against the source, per distributor. Diagnose by proving the cause with a number that matches the gap. Correct the rule. Prevent with a test that fails loudly, and watch it fail once so you know it works. Green ≠ right.

Hint

select distributor_id, product_code, round(min(units_sold)::numeric / avg(units_sold), 2), round(max(units_sold)::numeric / avg(units_sold), 2) from analytics.japan_sell_through group by 1, 2. Check your answer

On the fixed Japan model, normal weeks run from 0.41× to 1.57× of the average (10 distributor-and-product series). With 0.5× / 2× the test FAILS 6: six perfectly normal low weeks flagged, and by Friday nobody trusts the alarm. With 0.35× / 1.75×, just outside the normal range: PASS. A confident number from a tool gets checked less than the same number from a colleague. That is automation bias.
